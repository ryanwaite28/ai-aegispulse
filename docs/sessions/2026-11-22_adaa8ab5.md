- **Rate limiting stays in memory:** I chose `@nestjs/throttler` with per-pod memory, so the gateway still talks to no database.

## 1. Goal
Upgrade `rxjs-rabbitmq` (currently **2.2.3**) so that a production consumer can run it under a **least-privilege RabbitMQ user**, with **publisher confirms**, **bounded memory**, and **durable broker-side retry and dead-lettering**. The library must stay small and unopinionated: no application-specific envelope, naming scheme, or retry policy belongs in it. ## 2. Consumer context (why these requirements exist)
The first consumer is a multi-service, event-driven platform. Its messaging rules are non-negotiable:

1. **Topology is declared out of band.** A separate admin job declares exchanges, queues, and bindings. **Runtime users have no `configure` permission** (RabbitMQ permission regex `^$` for configure), and only `read` on their own queues and `write` on the exchanges they publish to. A runtime client must never call `queue.declare` / `exchange.declare` / `queue.bind` (non-passive), because the broker answers `403 ACCESS_REFUSED` and closes the channel.
2. **At-least-once delivery with publisher confirms.** A transactional-outbox relay marks a row `SENT` only after the broker **confirms** the publish. Unroutable messages must be detected (`mandatory` + `basic.return`), not silently dropped.
3. **Durable retry and DLQ.** Retries go through broker-side TTL delay queues: republish to a retry exchange with a routing key like `{queue}.retry.{tier}` and an incremented `x-retry-count` header. Dead letters are published to a topic DLX exchange with error headers. The original message is **acked only after the republish is confirmed**, and nack-requeued if the republish fails. No `setTimeout`-based in-process retry.
4. **Manual ack, bounded prefetch, bounded memory.** The process runs for weeks under Kubernetes with a 384 MiB memory limit.
5. **Graceful shutdown on SIGTERM.** Stop consuming, let in-flight handlers finish (≤ 20 s), then close. **No reconnect after an intentional close.**
6. **Readiness probes.** The service needs a cheap "connected and consuming" signal and a stream of connection and channel state changes.

Runtime: Node.js 24, TypeScript 6.0 strict (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`), ESM consumer (`"type": "module"`, `NodeNext`), amqplib **2.4.x**, rxjs **7.8.x**. pnpm with exact pins and a minimum-release-age policy, which the consumer **does not bypass**.
